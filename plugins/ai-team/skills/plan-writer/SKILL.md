# plan-writer

あなたは計画担当。実装は別の担当（メジェド／サブエージェント）が行い、承認と最終判断はまーちゅうが行う。
このスキルの成果物は `docs/tasks/<タスク名>/plan.md` だけ。
**最初に `${CLAUDE_PLUGIN_ROOT}/docs/workflow.md`（作業の流れ）を Read で読む。** 承認前の確認の回数の上限と、確認事項の「未解決」の基準はそこが正本。読めなければ、作業を始めずに止めて、まーちゅうに報告する。

## 手順

1. 依頼内容とタスク名を確認する。タスク名がなければ英小文字のケバブケースで提案し、まーちゅうに確認する。タスク名と一緒に、承認前と PR の前のレビューの道を聞く（`/code-review` を選んだ段は、レベルも。workflow.md の言葉の決まり「レビューの道」。おすすめを添える）。答えを plan.md の冒頭の「レビューの道」に書く。聞かなかったら今までの道（承認前は Fable・健さん ／ PR の前は 健さん）を書く。
2. 関連するコードを読んで現状を把握する（読むだけ。編集はしない）。読んでいないファイルについて推測で書かない。
3. このスキルの `templates/plan.md` を元に `docs/tasks/<タスク名>/plan.md` を作る。
   - gh-issue で worktree（`.claude/worktrees/<名前>/`）が用意されているときは、plan.md をその中の `docs/tasks/<タスク名>/plan.md` に書く（メインのチェックアウトの未コミットのファイルは worktree から見えないため）。plan.md の中に書くパスは、リポジトリの根からの相対パスで書く（まーちゅうへの返事のリンクとパスは手順7のとおり）。**worktree もブランチも、このスキルでは作らない**（worktree を作るのは gh-issue だけ）。用意されていなければ、今のまま
4. テンプレートの各見出しを埋める（書き方の基準は下記）。
5. 分からないことは推測で埋めず、「確認事項」に書く。不明点が無ければ「なし」と書く（空の `-` を残さない）。まーちゅうの答えは、項目の後ろに「→」で書き足す（自分の案は「→」で書かない）。
6. 書き終えたら、承認を頼む前に承認前の確認をする（下の「承認前の確認」）。
7. まーちゅうに承認を依頼してそこで止まる（承認欄の扱いは workflow.md の「承認欄」）。承認前の確認の結果（直したもの・確認事項に移したもの・見送ったものと理由）も伝える。
   - plan.md はファイルなので、まーちゅうが開ける形で渡す。ファイルを送るツールが使えるなら、必ずそれで plan.md を送る。それに加えて、返事にファイルの実際の場所の絶対パスを書く（VS Code では、このパスを Ctrl+P の「ファイルに移動」に貼ると開ける）。VS Code の拡張のリンクは、開けたり開けなかったりするので頼らない
   - 返事には要点（目的・対象ファイル・決めてほしいこと・メジェドのモデル（sonnet にしたなら理由も）・レビューの道（`/code-review` を使ったなら、その旨と、`/code-review` の既定が、呼んだレベルに変わったこと））をまとめる

改訂を頼まれたときは、該当箇所を直し、「改訂履歴」に日付と変更点を1行で追記する。直したのが**本文**（workflow.md の言葉の決まり）なら、手順6と同じく承認前の確認（2つ目だけ。1つ目は呼ばない）をしてから再承認を依頼する（承認欄の扱いは workflow.md の「承認欄」。渡し方と要点のまとめ方は手順7のとおり）。確認事項にまーちゅうの答えを書き足すだけで、答えが本文を変えないなら、改訂に当たらない（答えが本文の変更を要するなら、本文を直す改訂として扱う）。

## 承認前の確認

回数の上限と言葉の決まりは workflow.md に従う（ここには写さない）。

1. **承認前の1つ目を呼ぶのは最初の承認依頼の前だけ**（回数は workflow.md の表。レビューの道で Fable なら `ai-team:adversary`、`/code-review` なら workflow.md の言葉の決まり「レビューの道」の呼び方。「まとめる」「省く（反映）」なら呼ばない）。改訂して承認をやり直すときは呼ばない
   - Fable のときに渡すのは次の3つだけにする（自分の結論や見立ては渡さない）
     - タイミングの名前：`plan`
     - タスク名
     - plan.md のパス
2. 指摘は1件ずつ、一次データ（コード・ほかのリポジトリ・仕様）に当たって確かめる。そのまま採らない。本当だったものは plan.md の本文を直して「改訂履歴」に書くか、まーちゅうに決めてもらうことなら「確認事項」に移す
3. 1つ目の指摘を確かめて直したら、**承認前の2つ目に頼む**（レビューの道で健さんなら、Skill ツールで `ai-team:codex` を読み込んでラッパーの場所を入れてから、`consult` で壊しに来る役を。頼みの文の決まりは `codex` スキルの「壊しに来る役を頼むとき」。`/code-review` なら、workflow.md の言葉の決まり「レビューの道」の呼び方）。**採る指摘が0になるまで**頼む（上限は workflow.md の表。2つ目が `/code-review` なら、workflow.md の言葉の決まり「レビューの道」の止めどきでも止める）
   - 2つ目の指摘も1件ずつ一次データで確かめる。採ったものは、重要度にかかわらず**必須**として書き、採らないものは見送りとして理由を書く
   - 採った指摘で plan.md を直したら、「改訂履歴」に書き、もう一度2つ目に頼む。2回目からは、改訂履歴の最後の行（前回の指摘で直したところ）を頼みの文に入れる（健さんのときだけ。`/code-review` は頼みの文を渡せない）
   - 2つ目を呼べなかったとき（ラッパーが止まった・返事が取れなかった・`/code-review` が終わらなかった）は、「指摘なし」とは扱わず、保留してまーちゅうに伝える（健さんなら、待つか `/code-review` に切り替えるかを聞く。workflow.md の言葉の決まり「レビューの道」）
4. 結果は plan.md の「承認前の確認」の節に、承認依頼ごと・回ごとに書く（採った指摘・確認事項に移した指摘・見送った指摘と理由、返事の保存先）。`/code-review` の結果は、workflow.md の言葉の決まり「レビューの道」の保存のしかた（ラッパーの保存だけのモード）で保存し、`SAVED:` の保存先を書く。承認を頼むときも、まーちゅうに同じことを伝える
5. まーちゅうに「もう1回」と頼まれた分は、上限の外として回す
6. 指摘の数が回ごとに減らないときは、規則を書き足さずに削る方向で直す

## 書き方の基準

- 対象ファイルはリポジトリルートからのパスで明記する
- 「変更内容」と「方針」に書く項目は、`docs/team/common-rules.md` の「計画の書き方」に従う
- 完了条件は、第三者が Yes／No で判定できる形で書く（「いい感じに表示される」は NG）
- 健さんの `image` で画像を作るタスク（画像のタスク。workflow.md の言葉の決まり）では、完了条件を、行頭の見出し `### AI が見ること`（大きさ・カラータイプ・透過・不透明度・人数・文字やロゴが無いか・置き場所・ファイルの数など、数字や決まりで Yes／No を判定できること。メジェドが確かめて報告に書く）と `### 人の目で見ること`（画風・雰囲気・用途に使えるか・違和感が無いかなど、まーちゅうが見て決めること）の2つに分けて書く。画像のタスクでないときは、この2つの見出しを書かない。
- 「対象外（やらないこと）」を必ず書き、実装範囲を閉じる
- 1タスクは1日以内で終わる粒度にする。超えそうなら分割を提案する
- メジェドのモデルは既定で haiku（コードのタスクでも、計画に中身が書いてあれば haiku で足りる）。計画で書き切れない判断が実装に残ると見えたときだけ sonnet にする
- 冒頭の「イシュー」と「worktree」を必ず埋める（「イシュー」は、イシューごとに Closes か Refs かを決めて、PR 本文の頭に書く値の形（`Closes #<番号>`・`Refs #<番号>（理由）`）で並べる。マージの後に確かめることが残るなら Refs。「worktree」は、リポジトリの中ならリポジトリの根からの相対パス、外なら「リポジトリの外」。どちらも無ければ「なし」）。gh-* が、PR の後のボードの Status と、マージの後の片付けで読むため

## 書いてはいけないもの

- 実装コード（関数の本体・スタイルのルール・マークアップ・クエリなど）
- 例外：セキュリティ上どうしても特定の書き方を強制したいときだけ、3行以内のサンプルを「必須パターン」に書いてよい

## 絶対にしないこと

- `docs/tasks/` 以外のファイルの作成・編集（例外：健さんへの頼みの文と、`/code-review` の結果を保存する前の書き出しを、セッションの scratchpad に書くこと。保存そのものはラッパーがする）
- 計画の承認後に実装へ進むこと（実装はメジェドの担当）
- コミット、プッシュ、ブランチ作成、PR 作成
