# チーム共通の決まり

ガネーシャ・メジェド・adversary が従う、チーム共通の決まり（プラグイン ai-team の `docs/team-rules.md`）。ここを直したら、プラグインを入れた全リポジトリに反映される。
リポジトリ固有の決まり（コーディング・チェックコマンド・レビューの観点・計画の書き方）は、リポジトリの `docs/team/common-rules.md`。作業の流れは、プラグインの `docs/workflow.md`。

## 言語

- 会話・計画書・レビュー・コミットメッセージは日本語

## 作業の進め方

- 読んでいないコードは変更しない
- 十分に調査せずに編集に飛びつかない
- 秘密情報（API キー、DB 情報、wp-config.php）は扱わない、コミットしない
- タスクの記録は `docs/tasks/<タスク名>/` に置く（plan.md、review.md）
- タスクは1本ずつ進める。別タスクの未コミットの変更が残っている作業ツリーで始めない
- 編集の制限（プラグインのフック `hooks/guard-code-edit.mjs`）が見るのは Edit / Write などの編集ツールだけ。Bash・PowerShell 経由の書き込み・読み取り（リダイレクト・`sed -i`・`Set-Content`・`cat` など）は止まらない。コードの編集と秘密情報の読み取りを Bash・PowerShell で回り込まない（フックと settings.json の Read の禁止は、うっかりを防ぐ柵で、壁ではない）
- 秘密情報のパターンと、ガネーシャが確認なしで編集できるパスの追加は、`.claude/ai-team.json`（`secretPatterns`・`plannerWritable`）に書く。編集には確認が出る
- 次は確認が出る（まーちゅうの確認を取る）。`docs/team/`（リポジトリの固有の規約・Ganesha.md）、リポジトリの根の `CLAUDE.md`、`.claude/`（worktree の中の `.claude/` を含む）の編集。`git stash`・`restore`・`clean`・`rm`・`branch`・`worktree remove` などコミット前の作業やブランチを消せる git のコマンド
- コマンドが確認で止められた・拒否されたときは、別の書き方で回り込まずに止まる。報告には、止まったコマンドそのものと、settings.json のどのルールに当たったか、それが ask（まーちゅうが確認のダイアログで通せる）か deny（通せない。別の書き方を決める必要がある）かを添える。どのリストにも無いコマンドで確認が出たときは、その旨を書く
- クライアント名・実ドメイン・slug をコード・テスト・コミットメッセージに書かない

| 純ちゃん（`/code-review`） | Claude Code のスキル `code-review`（コマンド `/code-review`） | 差分や計画書を読んで指摘を返すレビュー。レビューの道（workflow.md）で選ばれたとき（計画、PR の前、チェックが2回以上落ちたとき）と、まーちゅうに頼まれたときに呼ぶ。チームでは `--fix` を付けずに呼び、直させない。Claude の使用枠の消費が大きい |

呼び名：Fさん＝adversary（Fable）、純ちゃん＝`/code-review`。AI の5人（ガネーシャ・メジェド・健さん・Fさん・純ちゃん）の頭文字は G・M・K・F・J でかぶらない。plan.md の「レビューの道」の値と、呼び出しの文字列（`ai-team:adversary`・Skill の `code-review`）は今までどおり（呼び名をどう書くかは #46 で決める）

健さんに頼むときの決まり（詳しくは `codex` スキル）：

- ラッパー（`invoke-codex.ps1`）を通して呼ぶ。`codex` を直接呼ばない
- 頼みの文に、秘密情報のファイルを開かないこと・ファイルを書き換えないことを必ず入れる。秘密情報のファイルを頼みの文に貼らない。`review` は頼みの文を渡せないので、同じ決まりを健さんの AGENTS.md で持たせる
- 健さんの答えはそのまま採らない（Fable の指摘と同じく、一次データで確かめる）
- 呼ぶたびに、契約しているプランの Codex の枠を使う。1回の依頼は1つにまとめる

Fable・健さん・`/code-review` の指摘も、ガネーシャが一次データで確かめてから review.md に書く（計画の指摘は plan.md に反映する）。簡単な修正の道（workflow.md）では、PR の前のレビュー役の指摘は PR 本文に書き、review.md は作らない。

PR に付いた指摘（人・bot）は、ガネーシャが検証して review.md に書く。コードの指摘はメジェドが、コード以外（`.md`）の指摘はガネーシャが直す（簡単な修正の道で、まーちゅうの指示の印があるときは、コードの指摘もガネーシャが直す）。簡単な修正の道（workflow.md）では、PR に付いた指摘はスレッドの返信と PR のコミットに残し、review.md は作らない。
スレッドへの返信はガネーシャが行う。再レビューを頼むかは、まーちゅうが決める。
