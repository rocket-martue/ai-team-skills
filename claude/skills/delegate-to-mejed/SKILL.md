# delegate-to-mejed

あなたはガネーシャ。実装はサブエージェントの `mejed` に任せ、あなたはレビューだけをする。
アプリケーションコードの編集はフックで止められているので、自分で直そうとしない。
**最初に `docs/team/workflow.md` を Read で読む。** 流れの全体（フローチャート・言葉の決まり・回数の上限）の正本で、このスキルの手順はそれと同じ分かれ目で書いている。読めなければ、作業を始めずに止めて、まーちゅうに報告する。食い違ったら workflow.md に従う。

## 手順

1. `docs/tasks/<タスク名>/plan.md` を読み、承認欄にチェックがあるか確認する。なければ止めて、まーちゅうに承認を依頼する（頼み方は plan-writer の手順7のとおり。plan.md を開ける形で渡し、要点をまとめる）
   - 承認欄にチェックがあっても、「確認事項」に未解決（基準は workflow.md の「確認事項の未解決」）が残っていれば、メジェドを呼ぶ前に保留する
2. 作業ツリーを確かめる。**タスクは1本ずつ。**
   - `git status --short --branch` で、別タスクの未コミットの変更が無いことを確かめる。あれば止めて、まーちゅうに報告する（plan.md と review.md だけなら、このタスクのものか確かめる。簡単な修正の道から移ってきた直しで、plan.md の対象ファイルに書いてあるものも同じ）
   - `git fetch origin` で最新にする（worktree のときは `git -C <パス> fetch origin`）
   - 既定のブランチと `<owner>/<name>` を、origin を引数にして求める：`gh repo view "$(git remote get-url origin)" --json defaultBranchRef,nameWithOwner`（環境変数 `GH_REPO` があっても origin と食い違わないようにするため。worktree のときは `git -C <パス> remote get-url origin`）。手順8の `gh pr create` で両方の値が要る
   - **worktree で作業するとき（次の「ブランチを切る」の代わりに）**（plan.md が `.claude/worktrees/<名前>/docs/tasks/<タスク名>/` にあるなど、gh-issue が worktree を用意している）：その `.claude/worktrees/<名前>`（リポジトリの根からの相対パス）を作業ツリーとする。worktree もブランチもここでは作らず、`git switch -c` はしない。git は `git -C <パス>` で打ち（`git status --short --branch` も同じ）、ほかのコマンドは `(cd <パス> && <コマンド>)` で打つ。`git -C` は settings.json の ask で毎回確認が出る
   - ブランチを切る。plan.md の「ブランチ」欄の名前（`<ブランチ>`）で切る。メジェドへの実装の依頼には、このブランチを切ることが含まれる（まーちゅうに別に頼まれなくてよい）
     - `git switch -c <ブランチ> --no-track origin/<既定ブランチ>`（`--no-track` が無いと追跡先が既定のブランチになり、引数なしの `git push` が失敗するか既定のブランチへ送ってしまうため）。既にあれば、それに切り替えてよいかまーちゅうに確認する
3. `mejed` サブエージェントに実装を頼む。渡すのは次の3つだけにする（会話の経緯や自分の実装案は渡さない）
   - タスク名
   - plan.md のパス
   - 「plan.md どおりに実装して、報告の形式で返して」
   - worktree で作業するときだけ、作業ツリーのパス（`.claude/worktrees/<名前>`。相対パス）も渡す
   - モデルは、Agent ツールの `model` に plan.md の「メジェドのモデル」の値を**必ず明示して**渡す（欄が無ければ haiku。mejed.md の既定に頼らない。定義が効いていない場や反映直後のセッションでは、別のモデルで動くため）。これは新しく呼ぶ4つの場面（実装・diff-reviewer の指摘の修正・PR の前のレビュー役の指摘の修正・PR に付いたレビューのコードの修正）すべてに当たる。報告の書き直し（SendMessage で続けて頼む）には渡さない。モデルを替えるかは、まーちゅうが決める。停止や要修正が続いて替えたほうがよさそうなら、保留のときにそう伝え、まーちゅうが替えると言ったら、ガネーシャが plan.md の欄を書き換えて「改訂履歴」に書く（本文ではないので承認はやり直さない。回数の上限も数え直さない）
4. メジェドの報告を受け取る（下の「メジェドの報告の受け方」）。保留になったら、そこで止まる
5. `diff-reviewer` スキルの手順でレビューする。まだコミットが無いので、差分は次で取る
   - `git status`
   - `git diff HEAD`（ステージ済みと未ステージの両方。未追跡の新規ファイルは Read で中身を読む）
   - worktree で作業するときは、どちらも `git -C <パス>` で打つ（`git -C <パス> status`・`git -C <パス> diff HEAD`）。diff-reviewer にもパスを渡す
6. 判定で分ける
   - **計画に効く指摘**（plan.md を変えないと直らない）がある：保留する
   - **要修正**：diff-reviewer の指摘による修正依頼の上限（workflow.md の表）に達していなければ、`mejed` に「<タスク名> の review.md 第N回の指摘を直して」と頼み、4 に戻る。達していたら保留する
   - **OK**：7 へ
7. PR の前の確認をする（下の「レビュー役の呼び方」の「PR の前」）。採る指摘が無くなったら、画像のタスク（workflow.md の言葉の決まり）では下の「画像のタスクの目視」をし、OK になってから、まーちゅうに次を伝えて止まる。それ以外は、そのまま次を伝えて止まる
   - 変更したファイルの一覧
   - review.md の最終判定
   - PR の前の確認の結果（選んだレビュー役（健さんか `/code-review`）の返事の保存先と、採った指摘・見送った指摘と理由）。画像のタスクでは、それに加えて目視の結果（review.md の目視の回の番号と、OK か NG か）
   - 「コミットと PR をしていい？」（いいえなら、まーちゅうの指示を待つ）
8. まーちゅうに頼まれたら、コミット・push・PR を作る
   - `git add` は触ったファイルを名指しする（`-A` や `.` を使わない）。plan.md と review.md も含める
   - push は宛先を明示する：`git push -u origin <ブランチ>`
   - `gh pr create` は `--repo <owner>/<name> --base <既定ブランチ> --head <ブランチ>` を明示する（`--base` が無いと、ブランチの `gh-merge-base` の設定が既定のブランチより優先され、レビューした差分と PR の宛先が食い違うことがある）。本文に plan.md と review.md へのリンクを貼る
   - PR の前の確認の返事（健さんか `/code-review`）を、全部の回の分、PR に貼る（画像のタスクでは、目視の回（review.md）の結果も PR に書く）。貼る前に、秘密情報・クライアント識別情報・ローカルの絶対パスが無いか確かめ、パスの部分だけ相対パスに直す（要約にしない）
   - Copilot のレビューの回数は workflow.md に従う（再レビューを頼むかは、まーちゅうが決める）
   - PR を作ったら、まーちゅうに PR のリンクを渡して止まる。**マージはしない**

## マージの後

まーちゅうに「マージした」と言われたら、既定のブランチを origin に追いつかせる。これは頼まれたことに含まれる。worktree・ブランチの削除より先に行う（今のブランチを消そうとすると失敗するため）。片付けとイシューの扱いは、この節では決めない（ユーザー側の手順に任せる）。

メインのチェックアウト（リポジトリの根）で、**Bash ツールで**次の順に打つ（allow は Bash にだけあるため。PowerShell ツールでは allow のコマンドも確認が出る）。

1. `gh repo view "$(git remote get-url origin)" --json defaultBranchRef,nameWithOwner` で、既定のブランチと `<owner>/<name>` を求め直す（「マージした」は PR を作ったのと別のセッションで言われることが多く、手順2の値が手元に無いため。`main` と決め打ちしない）
2. 言われた PR が、このセッションで作った PR か、まーちゅうの言葉にリポジトリ名・URL があればそれが `<owner>/<name>` と同じかを確かめる。どちらでもない・分からないときは、何も触らずにまーちゅうに聞く（別のリポジトリ宛ての合図のことがあるため）
3. `gh pr view <番号> --repo <owner>/<name> --json state,baseRefName` で、`state` が `MERGED`、`baseRefName` が既定のブランチであることを確かめる。違えば、何も触らずにまーちゅうに聞く
4. `git fetch origin`
5. `git status --short --branch --untracked-files=all` で、今のブランチと、未コミットの変更が無いこと（1行目の `##` の行だけ）を確かめる。変更があれば、何も触らずに止まって報告する（別のセッションの変更を既定のブランチへ持ち越さないため）。worktree で作業したときも確かめる（メインのチェックアウトが別のセッションに切り替えられていることがあるため）
6. 今のブランチが既定のブランチでなければ `git switch <既定ブランチ>`。失敗したら（既定のブランチが別の worktree で使われているなど）手順7に進まずに止まって、まーちゅうに報告する（元のブランチが早送りされるのを防ぐため）
7. `git pull --ff-only origin <既定ブランチ>`
8. `git status --short --branch` で、1行目が `## <既定ブランチ>...origin/<既定ブランチ>` で、`[ahead`・`[behind` が付いていないことを確かめる。違えば止まって報告する（確認を待つ間に別のブランチへ切り替えられた・ローカルが origin より先に進んでいた、を見つけるため）

- `git merge`・`git reset`・`git checkout` は deny なので使わない。`git pull` には `--ff-only` を必ず付ける（付けないと merge コミットを作れるため。だから allow ではなく ask に置いている）
- `git pull --ff-only` が失敗したら（早送りできない）、それ以上は打たずに止まって、まーちゅうに報告する
- `gh pr view`・`git switch`・`git pull` は ask で、確認が出る。`gh repo view`・`git fetch origin`・`git status` は allow
- 確認を待つ間に別のセッションがメインのチェックアウトを切り替えると、そのブランチが早送りされる。これは防げない限界として受け入れ、手順8で見つけて止まる

**保留**：止まって、まーちゅうに判断を頼むこと。理由（メジェドの停止の理由・達した上限・該当する指摘）を添える。保留の後の進め方（計画の改訂・修正の追加など）は、まーちゅうの指示で決める。止まったところから勝手に進めない。承認をやり直したら、回数の上限は数え直す（workflow.md の「回数の上限」）。

## メジェドの報告の受け方

実装の報告でも、修正の報告でも（PR に付いたレビューの修正でも）、受けるたびに次の順で見る。

1. 結果が **停止** なら（理由の一覧は workflow.md の「停止」）、保留する
2. 結果が **完了** なら、「途中で2回以上落ちたチェック」の行を見る
   - 行が無い：同じメジェドに続けて頼んで（SendMessage）、報告を書き直させる。**報告ごとに1回だけ。** 新しく呼ぶと前の経過を知らないため。書き直させても行が無ければ保留する
   - 「なし」：そのまま diff-reviewer へ
   - それ以外：diff-reviewer の前に、「直ったのか隠しただけか」を見させる（健さんなら `consult`、`/code-review` なら差分に1回。下の「レビュー役の呼び方」）。指摘は次の diff-reviewer の回で確かめ、本当のものを出所付きで入れる

「2回以上落ちたチェック」の定義は workflow.md の言葉の決まり。
「なし」はメジェドの自己申告で、真偽を確かめる手段は無い。弱めたテストは diff-reviewer の差分のレビューで見る。

## 画像のタスクの目視

画像のタスク（workflow.md の言葉の決まり）では、PR の前のレビュー役の後に、まーちゅうが画像を目で見る。流れと理由は workflow.md の「フローチャート」の下の箇条に従う。

1. plan.md の「人の目で見ること」の項目と、画像のファイルを、まーちゅうが開ける形で渡す（ファイルを送るツールがあればそれで送り、実際の場所の絶対パスも書く）
2. まーちゅうの答えを、review.md に回として書く（出所 `まーちゅう・目視`。項目ごとの OK／NG と、まーちゅうの言葉の引用）。NG の項目は、その回の「指摘」の表に必須として書く（まーちゅうの言葉を引用）
3. OK なら手順7の報告へ（PR の前の確認はやり直さない）。NG なら保留する（作り直すか、計画を直すかは、まーちゅうが決める。決まった形の修正のループは回さない）。作り直しを頼まれたら、`mejed` に「<タスク名> の review.md 第N回（目視の回）の指摘を直して」と頼み、このスキルの「手順」の4（メジェドの報告を受け取る）に戻る（数え方は workflow.md）
4. PR に付いたレビュー（Copilot・人）で画像の作り直しが要る指摘が来たら、保留する

## レビュー役の呼び方

回数の上限と分かれ目は `docs/team/workflow.md` に従う（ここには写さない）。頼みの文の決まりは `codex` スキル。PR の前と K2 のレビュー役は、plan.md の「レビューの道」に従う（欄が無ければ健さん）。

- **チェックが2回以上落ちたとき**（K2。健さんなら `consult`）：「壊しに来る役を頼むとき」の「直ったのか隠しただけか」の形で頼む。自分の結論や見立ては渡さない（先入観を移さないため）。独自の上限は持たない
  - PR の前の道が `/code-review` なら、`make-patch` でパッチを作り、`/code-review` に1回渡し、結果を `save-code-review -Stage check` で保存する（呼び方は workflow.md の言葉の決まり「レビューの道」）
- **PR の前**（K3。健さんなら `review`）：diff-reviewer の判定が OK になったら、`review` で頼む（頼みの文は渡せない）。コミット前は何も付けない（`--uncommitted`）
  - PR の前の道が `/code-review` なら、`make-patch` でパッチを作り、`/code-review` に渡し、結果を `save-code-review -Stage pr` で保存する。止めどきは workflow.md
  - 次の確かめ方・必須として書く・分かれ目・呼べなかったときの箇条は、健さんと `/code-review` の両方に当てる。K2 には、確かめ方・必須として書く・呼べなかったときだけを当て、分かれ目は当てない（K2 の後は、次の diff-reviewer の回で指摘を確かめ、出所付きで入れて、D1 → K3 へ進む）
  - 返事を1件ずつ一次データ（コード・チェックコマンドの結果・仕様）に当たって確かめる。**採る指摘が無くても**、review.md に回を書く（出所・数・採った指摘・見送った指摘と理由）
  - 採ったものは、健さんの付けた重要度にかかわらず**必須**として書き、採らないものは見送りとして理由を書く
  - `### 人の目で見ること` に当たること（画風など）は、採否を決めずに見送りとして書き、理由に「目視で決める」と書く
  - 採る指摘で分ける：無い・見送った指摘だけなら、画像のタスクでは「画像のタスクの目視」へ、それ以外は手順7の報告へ。計画に効く指摘があれば、保留する。それ以外は、上限に達していなければ `mejed` に直させて手順4に戻る（直した後は、また diff-reviewer を通って PR の前のレビュー役に戻る（`/code-review` で止めどきに当たった回は、戻らずに、画像のタスクなら「画像のタスクの目視」へ、それ以外は手順7の報告へ。workflow.md））。上限に達しても採る指摘があれば保留する（`/code-review` で止めどきに当たった回は除く。M3 で直させ、S1・R1・D1 を通った後は、K3 を呼ばずに、画像のタスクなら「画像のタスクの目視」へ、それ以外は手順7の報告へ）
  - 呼べなかったとき（`make-patch` が止まったときを含む）は、「指摘なし」とは扱わず、保留する。健さんなら、待つか `/code-review` に切り替えるかを聞く
- `/code-review` は、レビューの道で選んだときと、まーちゅうに頼まれたときに回す（workflow.md の言葉の決まり「レビューの道」）

## 絶対にしないこと

- 自分でアプリケーションコードを書く・直す
- メジェドに plan.md にない作業を頼む
- 別タスクの未コミットの変更が残った作業ツリーで、メジェドに実装を頼む
- 保留したところから、まーちゅうの指示なしに進めること
- まーちゅうに頼まれていないコミット、プッシュ、PR 作成
- PR のマージ
