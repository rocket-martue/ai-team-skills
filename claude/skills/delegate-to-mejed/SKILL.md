# delegate-to-mejed

あなたはガネーシャ。実装はサブエージェントの `mejed` に任せ、あなたはレビューだけをする。
アプリケーションコードの編集はフックで止められているので、自分で直そうとしない。
**最初に `docs/team/workflow.md` を Read で読む。** 流れの全体（フローチャート・言葉の決まり・回数の上限）の正本で、このスキルの手順はそれと同じ分かれ目で書いている。食い違ったら workflow.md に従う。

## 手順

1. `docs/tasks/<タスク名>/plan.md` を読み、承認欄にチェックがあるか確認する。なければ止めて、まーちゅうに承認を依頼する
   - 承認欄にチェックがあっても、「確認事項」に未解決（まーちゅうの答えが「→」に続けて書き足されていない項目。「なし」だけなら未解決は無い）が残っていれば、メジェドを呼ぶ前に保留する
2. 作業ツリーを確かめる。**タスクは1本ずつ。**
   - `git status --short --branch` で、別タスクの未コミットの変更が無いことを確かめる。あれば止めて、まーちゅうに報告する（plan.md と review.md だけなら、このタスクのものか確かめる）
   - main にいて、main が最新であることを確かめる
   - `feature/<タスク名>` を切る（`git switch -c feature/<タスク名>`。既にあれば、それに切り替えてよいかまーちゅうに確認する）
   - 着手したイシューが GitHub Projects のボードに入っているなら、Status を **In Progress** にする（下の「ボードの Status」）
3. `mejed` サブエージェントに実装を頼む。渡すのは次の3つだけにする（会話の経緯や自分の実装案は渡さない）
   - タスク名
   - plan.md のパス
   - 「plan.md どおりに実装して、報告の形式で返して」
4. メジェドの報告を受け取る（下の「メジェドの報告の受け方」）。保留になったら、そこで止まる
5. `diff-reviewer` スキルの手順でレビューする。まだコミットが無いので、差分は次で取る
   - `git status`
   - `git diff HEAD`（ステージ済みと未ステージの両方。未追跡の新規ファイルは Read で中身を読む）
6. 判定で分ける
   - **計画に効く指摘**（plan.md を変えないと直らない）がある：保留する
   - **要修正**：修正依頼が3回未満なら、`mejed` に「<タスク名> の review.md 第N回の指摘を直して」と頼み、4 に戻る。3回に達していたら保留する
   - **OK**：7 へ
7. PR の前の確認をする（下の「PR の前の確認」）。済んだら、まーちゅうに次を伝えて止まる
   - 変更したファイルの一覧
   - review.md の最終判定
   - PR の前の確認の結果（adversary と `/code-review` それぞれの、採った指摘・見送った指摘と理由）
   - 「コミットと PR をしていい？」（いいえなら、まーちゅうの指示を待つ）
8. まーちゅうに頼まれたら、コミット・push・PR を作る
   - `git add` は触ったファイルを名指しする（`-A` や `.` を使わない）。plan.md と review.md も含める
   - `gh pr create` は `--head feature/<タスク名>` を明示する。本文に plan.md と review.md へのリンクを貼る
   - PR に書いた `Closes` / `Refs` のイシューがボードに入っているなら、Status を **Review** にする（下の「ボードの Status」）
   - PR を作ったら、まーちゅうに PR のリンクを渡して止まる。**マージはしない**

**保留**：止まって、まーちゅうに判断を頼むこと。理由（メジェドの停止の理由・達した上限・該当する指摘）を添える。保留の後の進め方（計画の改訂・修正の追加など）は、まーちゅうの指示で決める。止まったところから勝手に進めない。承認をやり直したら、下の回数の上限は数え直す。

## メジェドの報告の受け方

実装の報告でも、修正の報告でも（PR に付いたレビューの修正でも）、受けるたびに次の順で見る。

1. 結果が **停止** なら（未承認・確認事項が残っている・計画どおりに実装できない・弱めないと通せない）、保留する
2. 結果が **完了** なら、「途中で2回以上落ちたチェック」の行を見る
   - 行が無い：同じメジェドに続けて頼んで（SendMessage）、報告を書き直させる。**報告ごとに1回だけ。** 新しく呼ぶと前の経過を知らないため。書き直させても行が無ければ保留する
   - 「なし」：そのまま diff-reviewer へ
   - それ以外：diff-reviewer の前に `adversary` を呼ぶ（タイミングは `repeated-failure`。下の「adversary の呼び方」）。指摘は次の diff-reviewer の回で確かめ、本当のものを出所付きで入れる

「2回以上落ちたチェック」は、common-rules.md の「チェックコマンド」の箇条1つが、1回の実装・修正の作業の中で2回以上失敗したもの。
「なし」はメジェドの自己申告で、真偽を確かめる手段は無い。弱めたテストは diff-reviewer の差分のレビューで見る。

## adversary の呼び方

- `adversary` サブエージェントに渡すのは次のものだけにする（自分の結論や見立ては渡さない。先入観を移さないため）
  - タイミングの名前：`repeated-failure` か `pre-pr`
  - タスク名と plan.md のパス
  - 差分の取り方：`git diff HEAD` と `git status --short`
  - `repeated-failure` のときは、メジェドの報告の「途中で2回以上落ちたチェック」の行
- 指摘をそのまま直させない。1件ずつ一次データ（コード・チェックコマンドの結果・仕様）に当たって確かめる

## PR の前の確認

diff-reviewer の判定が OK になったら、PR を出す前に、adversary と `/code-review` を並べて回す。同じ計画を読んだレビューは、同じ思い込みで読み飛ばすため。

**回すかどうか**

- 1巡目がまだなら回す
- 前の巡で**中身の指摘**（事実・判断・規則に効く指摘）を直していて、2巡目がまだなら回す
- それ以外（前の巡で採った指摘が無い・表記だけを直した・2巡済んだ）は回さずに手順7の報告へ

**1巡の中身**

1. `adversary` を呼ぶ（タイミングは `pre-pr`）
2. Skill ツールで `code-review` を呼ぶ。引数は `high --max-findings default` にする（対象は既定の「ブランチのコミットと未コミットの変更」のまま。対象を渡すとそれだけを見る。効力レベルと `--max-findings` は、渡さないと前に打った値を引き継ぐ）
3. 両方の指摘を1件ずつ一次データで確かめ、**採る指摘が無くても** review.md に回を書く（出所・数・採った指摘・見送った指摘と理由）
4. 採った指摘で分ける
   - 無い：手順7の報告へ
   - 計画に効く指摘がある：保留する
   - 2巡目で必須がある：直さずに保留する
   - それ以外：手順6の「要修正」と同じく、修正依頼が3回未満なら `mejed` に直させて手順4に戻る

## 回数の上限

| 上限 | 数え方 | 超えたら |
| --- | --- | --- |
| メジェドの報告の書き直し | 報告ごとに1回だけ | 保留 |
| メジェドへの修正依頼は最大3回 | 由来を問わず合算（diff-reviewer・repeated-failure・PR の前の確認） | 保留 |
| PR の前の確認は最大2巡 | 1巡 = adversary（pre-pr）と `/code-review` を1回ずつ | 2巡目で必須が出たら、直さずに保留 |
| repeated-failure の adversary | メジェドの完了の報告ごと。独自の上限は持たない | 修正依頼の上限で止まる（PR の前までで多くて4回） |

- 数えた値は review.md の回の「数」に書く（修正依頼の何回目か・PR の前の確認の何巡目か）。セッションをまたいでも数え直せるようにするため

## ボードの Status

- 手順は `~/.claude/skills/gh-flow/references/project-status.md` に従う。イシューごとに `projectItems` を読み、ボードに入っているときだけ動かす（入っていなければ何もしない）
- 動かしたら読み戻して確かめる。選択肢の名前（In Progress / Review）がボードに無ければ飛ばして、まーちゅうに一言伝える
- マージ後（`Closes` が Done になったかの確認、`Refs` を In Progress に戻す）は `gh-wrapup` スキルで行う

## 絶対にしないこと

- 自分でアプリケーションコードを書く・直す
- メジェドに plan.md にない作業を頼む
- 別タスクの未コミットの変更が残った作業ツリーで、メジェドに実装を頼む
- 保留したところから、まーちゅうの指示なしに進めること
- まーちゅうに頼まれていないコミット、プッシュ、PR 作成
- PR のマージ
