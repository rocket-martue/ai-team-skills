## 目的

画像のタスクでも、PR の前の健さんの `review`（K3）を回す。K3 の後に、まーちゅうが画像を目で見る段（EYE）を置く。あわせて、#40 の差分の `/code-review` で出た指摘（#41 の本文の1〜8と、コメントの9〜12）を片付ける。

## 背景・前提

- #40（#22）で、画像のタスクでは K3 を回さず、代わりに EYE を置いた。理由は「画像を作った健さんに確かめさせないため。`review` には頼みの文を渡せず、画像だけを外せない」（`repo-files/docs/team/workflow.md:84`）
- そのため、画像のタスクに入った画像以外の変更（置き場所の記録など）が、外のレビューを通らない。#41 の指摘1・2・5・7・9 はここから来ている
- #22 で困ったのは画風（人の目で見ること）で、健さんが自分の画像を確かめた中身は、大きさ・カラータイプ・透過（AI が見ること）だった（ganesha-mejed-channel の `docs/tasks/ken-character/review.md` の第2回：「`ken.png` は 1024×1536・RGBA で、白・黒の背景に重ねても背景の残りは無い」）。画風は今は EYE が受け持っている
- まーちゅうの決めたこと（2026-10-11。会話で聞いた）：画像のタスクでも K3 を回す。順は、diff-reviewer の OK → K3 → EYE
- EYE を K3 の後に置くのは、K3 の指摘で画像を作り直したときも、最後の画像をまーちゅうが見るため
- 健さんの K3 の返事のうち、`### 人の目で見ること` に当たること（画風など）は、採否を決めない（EYE で決める）。`### AI が見ること` に当たること（大きさ・透過など）は、ほかの指摘と同じく一次データで確かめて採否を決める（数字で決まるので、作った人が見ても先入観の問題は小さい）
- 指摘ごとの扱い（#41 の番号）
  - 1（見分け方が見出しの文字だけ）：K3 が必ず回るので、見出しが目印になるのは EYE だけになる。見出しを書き忘れると EYE が抜けるので、diff-reviewer が「差分に新しい画像のファイルがあるのに、完了条件に見出しが無い」を計画に効く指摘として拾う（plan.md の言い回しで見ると、見出しの文字から本文の言い回しに問題が移るだけなので、差分のファイルで見る）。見出しが余計にあっても、まーちゅうに見てもらう段が1つ増えるだけ
  - 2（画像のタスクに入れてよいものが開いている）：K3 が回るので、「画像と置き場所の記録だけを入れる」の決まりは要らなくなる。plan-writer から消す
  - 3（作り直した画像が残る）：mejed.md の「既存のファイルは上書きしない（別の名前にする）」を、「作業を始める前から既定のブランチにあったファイルは上書きしない。このタスクで置いた画像を作り直すときは、同じ名前で置き換える」にする
  - 4（手順7の参照切れ）：delegate-to-mejed の手順7を、「健さんの呼び方」の「PR の前」を指す形に直す
  - 5（弱めたテストの見張り）：K3 が回るので、`repo-files/docs/team/workflow.md:103` は今のままで正しくなる。直さない
  - 6（AI 側の項目の結果の書き場所）：「2回以上落ちたチェック」の定義に、plan.md の `### AI が見ること` の項目を足す。メジェドには、通らない項目を通るまで直させる（今は確かめて報告するだけで、直す決まりが無い）。報告の「チェックコマンドの結果」の行の「無い」は、チェックコマンドも `### AI が見ること` の項目も無いときだけにする。項目が2回以上落ちたときの K2（健さんの consult）で、健さんが画像のファイルを読めるかは確かめていない。#83 の K3（read-only の sandbox）では、健さんは PNG の大きさ・カラータイプ・透過を読んで返している（上の review.md の第2回）ので、読める見込み
  - 7（画像だけを外せていない）・9（K3 を回す選択肢が無い）：K3 を回すことで片付く
  - 8（役割の表に例外が無い）：K3 が回るので、`repo-files/docs/team/common-rules.md:45` と `README.md:8` は今のままで正しくなる。直さない
  - 10（例外の書き写し）：「画像のタスクでは K3 を回さない」の書き写しを全部消す。EYE の手順は workflow.md と delegate-to-mejed にだけ置き、README は要約の1か所だけにする。delegate-to-mejed にある「2回以上落ちたチェック」の定義の書き写し（`claude/skills/delegate-to-mejed/SKILL.md:83`）も、workflow.md を指す形にする
  - 11（PR に付いたレビューの扱う順）：diff-reviewer の「PR に付いたレビュー」の手順4で、画像の作り直しが要る指摘の箇条を先頭に移し、「あれば、ほかの指摘も直さずに保留する」にする
  - 12（目視で NG の後の戻り先）：NG なら保留は変えない。目視の回の NG の項目は、ガネーシャが「指摘」の表に必須として書く（メジェドは「必須」から直すので、○／× だけだと直す対象が無い）。まーちゅうに作り直しを頼まれたら、メジェドに目視の回の必須を直させ（M2 と同じ頼み方）、S1・R1・D1・K3 を通って EYE に戻る。上限に数えないのは、まーちゅうに頼まれた作り直しの依頼1回だけ（`repo-files/docs/team/workflow.md:98` の「頼まれて回す分は上限の外」）。戻り道の D1 の要修正と K3 は、流れの中で回るのでふつうに数える。PR の前の健さんをすでに5回呼んでいたら、戻り道の K3 は呼ばずに保留する（上限の表は最大5回のまま）。計画を直すなら P1 に戻る
- このリポジトリのチェックコマンド（このタスクに限る）：`node claude/hooks/test-guard-code-edit.mjs` と `node claude/skills/codex/scripts/test-invoke-codex.mjs`（文書の変更では結果が変わらないが、壊していないことを確かめるために打つ）
