## 流れ（`-Mode review -Container`）

コンテナには git の履歴を持ち込まない。**送るもの（写す候補の名前と差分）を先に決め、その名前を1回の `check` で確かめてから、中身を写す。確かめた後は、候補の一覧と差分を作り直さない。docker は、この PC での確かめ（1〜5）が全部通ってから呼ぶ。** 写しも差分も、`-WorkingDirectory` によらず、リポジトリの根（`git rev-parse --show-toplevel`）から作る。

1. 今の確かめ（設定ファイル・review に渡る変更の秘密情報）をそのまま通す。`container` が無ければ止める
2. この PC の codex の版（`findCodex` に `--version`）と、`<CODEX_HOME>/AGENTS.md` があるか・コンテナのレビューの印の行（`<!-- ai-team: container-review v1 -->`。テンプレートの、コンテナのレビューの節の頭に置く）が入った版か、を見る。どれかが無ければ止める（文で照らさないのは、自分用に書き換えた AGENTS.md でも印の行だけで見分けるため）
3. 以後この流れで打つ git（4・5 と、`-Container` のときの 1）には、全部 `-c core.fsmonitor=false` と `--no-optional-locks` を付ける（fsmonitor のフックを動かさない・索引を書き戻さない）。clean・process のフィルターは止めない（D12）
4. 送るものを決める（この PC の一時ディレクトリ `makePrivateTempDir` に置く。中身は `repo/` と、`review.diff`・`prompt.md`・空の `out/` を入れた `review/`）
   - 差分：1回の git で、パスの一覧と差分を一緒に作る（`git -c core.quotePath=false -c diff.noprefix=false -c diff.mnemonicPrefix=false diff --patch-with-raw -z --no-ext-diff --no-color --no-textconv --no-renames --submodule=short --src-prefix=a/ --dst-prefix=b/ <比べる先>`）。比べる先は、`-Base` 無しなら `HEAD`、ありなら `git merge-base <Base> HEAD` の値。出力の頭は `:` で始まる raw の項目（`:<メタ>\0<パス>\0` の並び）で、項目が尽きたところの空の項目（`\0`）の次からが差分。raw のパスを「差分のパス」として取り、差分を `review.diff` に書く。出力が空なら、差分のパスも無い
   - 写す候補：`git ls-files -z -co --exclude-standard` から、`lstat` で見てディスクに無いもの（消したファイル）を除いたもの（壊れたシンボリックリンクは、ディスクにあるのでリンクとして 5 で止まる）
5. 名前で確かめる（D10。中身はまだ写していない）。次のどれかがあれば止める（どのパスかは手元にだけ出し、健さんには送らない）
   - 秘密情報：差分のパスと写す候補の全部を、1回の共有モジュールの `check` に渡し、終了コード 3 なら止める（今の 1 と同じ口。設定ファイルはこの1回で読むので、判定に使う設定と送るものがそろう）
   - サブモジュール（`.gitmodules` がある、または `git ls-files -s` に `160000` の項目がある）
   - `/` で終わる項目（未追跡の入れ子のリポジトリ）
   - 名前に制御文字（`\x00-\x1f`・`\x7f`）・U+2028・U+2029 を含むもの（差分のパスも）
   - リンク：リポジトリの根の実体（`fs.realpathSync.native`）を基準に、候補の実体（同じく `.native`）が「根の実体＋候補の相対パス」と違うもの（根より下で、自分か親のどれかがシンボリックリンク・ジャンクション）。根より上のリンク（Mac の `/var` など）と、根の綴りの大文字小文字は比べる対象に入らない。比べ方は `sameLocation`（Windows だけそろえる）。止める文は「リンクか、綴りの大文字小文字が索引とディスクで違う」とする（Mac の既定の APFS で、名前の大小だけ変えたファイルも、止まる側に倒すため）
6. 写す：5 を通った候補を、`repo/` にバイトのまま写す。写す直前にもう一度 `lstat` し、リンクに変わっていれば止める
7. `docker` の向き先を決める：`DOCKER_CONTEXT` があれば止める。`DOCKER_HOST` があれば、それが `unix://`・`npipe://`（この PC）でなければ止め、あればそれを使う（Linux の rootless Docker の標準の形）。無ければ、`docker context show` の context のエンドポイント（`docker context inspect`）がこの PC でなければ止め、以後の `docker` には全部 `--context <その名前>` を付ける（途中で既定の context が変わっても、向き先を変えない）。`docker info` が通らなければ止める
8. イメージ `ai-team-codex:<版>` が無ければ作る。build のコンテキストは、プラグインの中の `container/` のフォルダだけ（`docker build -t … <プラグイン>/skills/codex/container`。対象のリポジトリをコンテキストにしない）。Dockerfile は `WORKDIR /work/repo`。作ったら、ほかの版の `ai-team-codex` のイメージを消す（強制終了で残ったコンテナが使っていて消せなければ、続けて、消せなかったことと消し方を標準エラーに出す）。npm にその版が無ければ止める
9. ログインを確かめる：`docker run --rm --label ai-team-codex=1`（ログインのボリューム `ai-team-codex-home` だけを付ける）で `codex login status`。無ければ README のログインの手順を出して止める
10. 作業用のボリュームを作る（呼ぶたびの名前。ラベル `ai-team-codex=1`）。作ったらすぐ後始末に登録する
11. **準備のコンテナ**：`docker create --rm --label ai-team-codex=1 -w /work/repo`（作業用のボリュームを `/work` に。ログインのボリュームは付けない。ネットワークあり）。作ったらすぐ後始末に登録する → `docker cp <一時ディレクトリ>/repo/. <コンテナ>:/work/repo`（中身を `/work/repo` の直下に置く）→ `docker start -a` で `container.setup` を打つ。写す・打つのどれかが失敗したら止める
12. **健さんのコンテナ**：`docker create --label ai-team-codex=1 --security-opt seccomp=unconfined -w /work/repo -e TMPDIR=/tmp`（`--rm` は付けない。作業用のボリュームを `/work` に、ログインのボリュームを `/root/.codex` に）。作ったらすぐ後始末に登録する → `docker cp` で、AGENTS.md を `/root/.codex/AGENTS.md` に、`docker cp <一時ディレクトリ>/review <コンテナ>:/review` で `review.diff`・`prompt.md`・空の `out/` を写す（`/review` はこのコンテナだけの場所で、準備と共有するボリュームの外。`container.setup` が `/work` に置いたリンクを通って書き込むことが無い）→ `docker start -a` で、決まった文字列の `sh -c '[ -d /work/repo ] && [ ! -L /work/repo ] || exit 97; exec codex exec --ephemeral --skip-git-repo-check -s workspace-write -C /work/repo -o /review/out/last-message.md "$@" - < /review/prompt.md' sh` を打つ（頭で、`container.setup` が `/work/repo` をリンクにすり替えていないかを確かめる。97 で終わったら、健さんを起こさずに止める）。この PC の `config.toml` の `model`・`model_reasoning_effort` があれば、`-c` とその値を `sh` の後ろの引数として足す（`"$@"` で渡るので、`sh -c` の文字列には入らない）。出力は今の `invokeCodex` と同じく、進み具合のログとして一時ファイルに流す
13. 頼みの文（ラッパーが組み立てる。`prompt.md`）：頭は「ガネーシャから（コンテナの中のレビュー）」。見る差分は `/review/review.diff`、作業ツリーは `/work/repo`（git のリポジトリではない）、未追跡のファイルの一覧、`container.test` を打って結果も根拠にすること、作業ツリーのファイルを書き換えないこと、指摘の書き方（`/work/repo` からの相対パスの ファイル:行 と重要度）
14. `docker cp <健さんのコンテナ>:/review/out/last-message.md` で返事を取り出し、標準出力に出す
15. 後始末（今の `cleanups`。D11）：コンテナ（`docker rm -f`）→ 作業用のボリューム → 一時ディレクトリ の順で消す（ボリュームは、使っているコンテナがあると消せないため）。どれかの消し方が失敗したら、続きも試したうえで、残ったものの名前と消し方を標準エラーに出す（終了コードは変えない）。この PC のリポジトリには何も書かない

`docker` は `codex` と同じく、シェルを通さずに起動する（`spawnSync` に引数の配列。Windows は PATH から `docker.exe` を探す）。

`-Mode check -Container`：1（設定ファイル。`container` があるか）・2・7・8・9 を行う。ログインが無ければ、ログインのコマンド（そのイメージを使うもの）を出す。新しい PC では、これを先に打ってからログインする。`-Container` 無しの `check` は今までどおり codex が無くても打てる。

テストでの差し替え：ラッパーを import できる形にし（直接起動されたときだけ動く）、テストの入口（テストのフォルダの中のファイル）から `docker` の起動の仕方を偽物に差し替える。環境変数などの、リポジトリの設定から差し込める口は作らない。

## 残る危険（まーちゅうに知っておいてほしいこと）

- 健さんのコンテナでテストを打つと、依存パッケージ（11 で入れたもの）のコードが、ログインのボリュームを読める場所で動く。Codex の sandbox（`workspace-write`）はネットワークを止めるので外には直接出せないが、読むことはできる。手元でテストを打つときと同じく、依存パッケージを信じる前提になる
- `container.setup` と `container.test` はリポジトリの設定ファイル（コミットされ、PR で変えられる）から来る。手元で `npm test` を打つのと同じ重さとして扱う
- 強制終了されると、コンテナ・作業用のボリューム・一時ディレクトリ（作業ツリーの写し）が残る。コンテナの中の codex は、ラッパーが死んでも最後まで走ることがある（D11）
- 改行コード：作業ツリーはこの PC のバイトのまま写す。テストが改行コードに頼っていると、コンテナと手元で結果が違うことがある
- 追跡した後で無視に足したファイル（`vendor/` など）は写る（秘密情報なら 5 で止まる）
- 名前を確かめてから写すまで（5→6）の間に、同じ名前のファイルの中身が変わると、変わった中身が写る（名前の確かめは変わらないので、秘密情報の名前のファイルは入らない）
- この PC の git の設定（clean・process のフィルターなど）は信じる（D12）。設定にリポジトリの中のスクリプトを書いていると、PR で変えたスクリプトがこの PC で動く（今のラッパーや普段の git でも同じ）
- 名前を確かめてから写し終えるまでの間に、同じ PC の別のプロセスが親のフォルダをリンクにすり替えると、リンク先の中身が写る（同じ PC で同時に書き換えられる相手は、守る相手にしていない）
- `container.setup` は作業用のボリューム（`/work`）を自由に書き換えられる（リンクを置くなど）。健さんのコンテナで使う頼みの文・差分・返事は `/review` に置くので、それには届かない
- WordPress の案件（追跡している `wp-config.php` があるなど）では、D10 で止まって使えないことが多い（D5 で対象は Node）
- ログインには、ChatGPT の設定でデバイスコードのサインインを一時的にオンにする必要がある（#39）
