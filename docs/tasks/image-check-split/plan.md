## 目的

健さん（Codex）の `image` で作った画像を差分に入れるタスク（画像のタスク）で、画像のチェックを「AI が見ること」と「人の目で見ること」に分ける。画像を作った健さんには、PR の前の確認（`review`）をさせない。代わりに、diff-reviewer が OK になった後に、まーちゅうが画像を目で見る段を入れる。

## 背景・前提

- 反映したリポジトリ（ganesha-mejed-channel）の画像のタスク（rocket-martue/ganesha-mejed-channel#83。記録は `docs/tasks/ken-character/review.md`）で、2つの問題が分かった（#22）
  - 画像を作った健さんが、PR の前の確認（`review`）で自分の画像を確かめ、「修正が必要な問題は無し」と返した（同 review.md の第2回）。作った人と確かめる人を分けていない
  - 画風が参照のキャラより写実に寄りすぎで、動画には使えなかった。数字で決めた完了条件（大きさ・透過など）は全部通っていて、まーちゅうが見て初めて分かった（同 review.md の第1回の「気づいたこと」）
- まーちゅうの決めたこと（2026-10-07。#22 の本文）：「AI が見ること」（大きさ・カラータイプ・透過・不透明度・人数・全身・文字やロゴが無いか・置き場所・ファイルの数・`git status`）はメジェドが確かめ、ガネーシャが読み直す。画像を作った健さんには確かめさせない。「人の目で見ること」（画風がそろっているか・キャラの雰囲気・実在の人物に似すぎていないか・用途に使えるか・違和感が無いか）は、まーちゅうが画像を見て判断する
- 健さんの `review` には頼みの文を渡せない（`claude/skills/codex/SKILL.md:67`）。差分を丸ごと見るので、「画像だけは見ない」とは頼めない。だから、画像のタスクでは PR の前の健さんの `review` を回さない
- まーちゅうの答え（2026-10-11。計画を書く前に会話で聞いた）
  - PR の前の健さんの `review` の代わりは、何も置かない。「AI が見ること」は、メジェドが確かめ、ガネーシャが diff-reviewer で読み直す（#83 でもそうしていた。同 review.md の第1回）
  - まーちゅうが画像を目で見る段は、diff-reviewer の OK の後（今の健さんの `review` の位置）に入れる。透過が壊れた画像を見せずに済む
  - 目で見て NG のときは、保留して指示を待つ。画風の直しは、計画に書いた頼みの文に効くことが多いので、決まった形では回さない
- 今の流れ（`repo-files/docs/team/workflow.md:35`）は、diff-reviewer が OK なら必ず健さんの `review`（K3）に進む。画像のタスクの分かれ目は、workflow.md・スキルのどこにも無い
- 「画像のタスク」を見分ける目印は、plan.md の「完了条件」の節の中にある、**行頭の見出し `### 人の目で見ること`** にする（以下「目印の見出し」）。plan-writer が、健さんの `image` で画像を作るタスクのときに、完了条件を見出し `### AI が見ること` と `### 人の目で見ること` に分けて書く。delegate-to-mejed と diff-reviewer は、目印の見出しがあるかで分かれ目を決める。文字列が本文やコメントに出てくるだけでは目印にならない（雛形のコメントは plan.md に残るため。例：`docs/tasks/image-check-split/plan.md` の承認欄の下のコメント）。雛形のコメントは、行頭を `###` にしない書き方にする
- 画像のタスクでは健さんの `review` を回さないので、画像以外の変更（コードや規約の直し）を同じタスクに入れると、その変更も健さんに見てもらえなくなる。だから、画像のタスクには、画像と、その置き場所の記録（README の1行など）だけを入れる、と plan-writer に書く
- #3 の「workflow.md を簡単にする」方向と食い違わないよう、足すのは分かれ目1つと、短い箇条だけにする。回数の上限の表は変えない（目視には回数を数えるものが無い。NG なら保留するので）
