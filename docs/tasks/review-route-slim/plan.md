## 変更内容

### 1. 計画の段階：選んだレビュー役を1回ずつ

- 承認を頼む前に、計画のときに選んだレビュー役（Fさん（タイミング `plan`）・健さん（`consult`）・`/code-review` のうち1人以上。既定は Fさんと `/code-review`）を1回ずつ回す（最初の承認依頼も、改訂後の再承認も同じ）。呼び方は、Fさんは今の承認前の1つ目、健さんは今の承認前の2つ目（codex の「壊しに来る役を頼むとき」の「計画のレビュー」）、`/code-review` は今の「レビューの道」の承認前の書き方（保存は `save-code-review -Stage plan`）のまま。並べて回してよい
- `/code-review` のレベルは既定 `medium`。ガネーシャが変えたほうがよいと思ったときだけ、理由を添えてまーちゅうに聞く（聞かなければ `medium`）
- 指摘は1件ずつ一次データで確かめ、本当のものは本文を直すか確認事項に移す。直した後にもう一度回さない
- 回せなかった・結果が取れなかったときは、今までどおり保留する
- 消すもの
  - workflow.md：フローチャートの承認前の段（承認依頼の前の分かれ目とループ。U1 には計画の `/code-review` の後から入る）、「承認前の1つ目・2つ目」「別々・まとめる」「省く（反映）」の決まり、上限の表の承認前の2行、承認前の止めどき、「承認をやり直したら回数は数え直す（承認前の1つ目は数え直さない）」の括弧書き
  - plan-writer：手順1で承認前の道を聞くこと、「承認前の確認」の1〜6（選んだレビュー役を1回ずつ回す数行に置き換える）
  - plan.md の雛形：「承認前の確認」は、承認依頼ごとに1つの見出し（`### 承認依頼N（YYYY-MM-DD）`）と、採った・確認事項に移した・見送った（理由）・返事（健さんと `/code-review` の保存先）の4行だけにする（Fさんの報告には保存先が無いので、採否だけを書く）
  - codex：「壊しに来る役を頼むとき」の「計画のレビュー」の「2回目からは、改訂履歴の最後の行…」（計画の段は1回だけになるため）。「計画のレビュー」そのものは残す
- 承認前の指摘を plan.md に「必須として書く」決まりは消す（plan.md の本文を直すだけで、必須・推奨の区別は使わない）

### 2. PR の前に Fさんを1回

- 呼ぶかは計画のときに選ぶ。既定は回す（`Fable`）。値は「レビューの道」の PR の前に書く（変更内容4）。おすすめは、今の PR の後の段のおすすめをそのまま移す（手順を書く PR・設計の判断が入るもの・ほかのリポジトリとの約束に効くもの・全リポジトリに効くプラグインの中身の大きい直しは回す、小さい直しは回さない）
- 順番：diff-reviewer の OK（D1）→ Fさん（選んだときだけ。1つの承認依頼につき1回）→ PR の前のレビュー役（K3。今までどおり、採る指摘が0になるまで最大5回）
  - 呼んだかは、review.md の出所 `Fさん・pr` の回と承認依頼の番号で見る。途中で終わった・読めなかった回は、呼んだことにしない
- Fさんは、最初からフォアグラウンドで呼ぶ（パッチは作業ディレクトリの外の scratchpad にあり、バックグラウンドでは確認を受けられずに読めないことがあるため）
- 渡すもの：タイミングの名前 `pr`・タスク名・plan.md のパス・作業ツリーのパス・パッチのパス
  - パッチは、ガネーシャがラッパーの `make-patch` で scratchpad に作る（K3 の `/code-review` と同じ）。止まった・終了コード 4 のときは、Fさんを呼ばずに保留する
  - 今の PR の後の「呼ぶ前の秘密情報の照らし（`git diff -z` と共有モジュールの `check`）」と、adversary.md の `git diff` の取り方と `git fetch origin` は消す
- 結果の扱いは K3 と同じ：計画に効く指摘・画像の作り直しの指摘は保留、ほかは1件ずつ一次データで確かめ、review.md に回を書き（出所 `Fさん・pr`。採ったものは必須）、メジェドに直させる（M3 と同じ頼み方）。直した後の D1 の要修正は diff-reviewer の修正依頼として数え、Fさんの回は K3 の上限に数えない
- Fさんの報告は PR 本文に貼らない。採否は review.md の回に残す（Fさんの報告には保存先が無く、セッションが変わると原文が手元に無いため）
- K2 は、Fable を除いた PR の前のレビュー役に合わせる
- 消すもの
  - workflow.md：フローチャートの PR の後の段、レビューの道の「PR の後」の段（値・選び方・おすすめ・呼ぶ前・結果の扱い・直した後・コミット）、上限の表の「PR の後（Fさん）」の行。「PR に付いたレビュー（PR の後の Fさん・人・bot）」は「（人・bot）」にする
  - delegate-to-mejed：手順8の PR の後の Fさん（1〜6）。「結果を確かめて報告したら」は「PR のリンクを渡して止まる」に戻す
  - diff-reviewer：「PR に付いたレビュー」の Fさんの読み替えの段落
  - review.md の雛形：出所の「（PR の後の Fさんの回）」、数の「（PR の後の Fさんを含む）」
- 簡単な修正の道：「PR の後の Fさんは回さない」を「Fさんは回さない（plan.md が要るため）」にする

### 3. PR の前のループで削る

delegate-to-mejed の「レビュー役の呼び方」の「PR の前」に、次を入れる（plan-writer の6を移す）。

- K3 の回ごとに、採った指摘の数を、まーちゅうへの報告に書く（review.md の回の指摘の表で数えられる）
- 採った指摘の数が回ごとに減らないときは、review.md の「修正方針」を、足す直し方（条件・例外・注記を足す）ではなく、消す・まとめる直し方で書く。足した文やコードが、次の回でまた指摘されるため
- 削ったことで外れた細部は、review.md のその回の「見送った指摘」に「削った（理由）」として残す（イシューにするかは、まーちゅうが決める）

## 方針

- 文書の直しだけ。フック・ラッパー・テスト・settings.json・健さんの AGENTS.md は触らない（`make-patch` はそのまま使う）
